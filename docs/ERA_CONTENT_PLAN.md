## Context

`dss-mac-docker` provisions DSS 11.x-15.x, but a provisioned node is nearly
empty. The Upgrade Planner skill needs a node that *looks real* to exercise its
paths — plugins, code envs and projects of the era — with **true positives**
(need remediation to upgrade), **true negatives** (upgrade cleanly), and
projects that should land **in** and **out of scope**.

A related bug, now diagnosed: admin is installed as `DATA_SCIENTIST`, a profile
only the 2018 licence offers, so under the 2024 licence DSS silently demotes it
to
`EXPLORER`. Slices 1-3 were seeded through the global admin API key while admin
was demoted, so this does **not** block API-key-driven creation — Phase A1 finds
out exactly which follow-up actions it does block.

## What shapes the design

- **Profiles follow the licence** — measured on 11.2.0, 12.6.7, 13.5.7 and 14.7.3
  (measurements kept locally, not published):
  `SAER` → `DATA_SCIENTIST`, `enterprise-fy2023-1` → `DESIGNER`, `*-fy2025-1` →
  `FULL_DESIGNER`, identically on every version. DSS 11.2.0 cannot use any 2025
  licence, and `set-license` still exits 0 for them.
- **Official per-major catalogs, no login:**
  `update.dataiku.com/dss/<major>/tutorials/list.json` (Solutions, tutorials,
  samples — at the version belonging to that era) and
  `update.dataiku.com/dss/<major>/plugins/list.json`. Older plugin versions:
  `downloads.dataiku.com/public/dss-plugins/<id>/` or git tags. Solutions carry
  their deps (`python-envs/<n>/desc.json`). The host downloads and uploads, so the
  node needs no internet.
- **Python per DSS line:** 12 = 2.7, 3.6-3.11 · 13 = 3.8-3.11 · 14 = 3.9-3.14 ·
  15 = no new 3.6-3.8. A code env needs its interpreter **in the image**.
- **The Planner's rules** (consumer-owned; summarised only to choose content):
  old-Python envs, unmaintained/superseded/removed plugins, the 6 deprecated
  `CustomCode_*` types, code-recipe VALIDATE at ≥14; scope via status, runs,
  apps, sample prefixes. `decide()`: **any active signal → MIGRATE**, even on a
  sample project; EXCLUDE needs **no execution history at all**.
- **Detection gaps** that cannot fire live — the most valuable content:
  `CustomCode_hubspot` never links to its plugin; R envs never graded; `cpython`
  never env-linked (#93); `params: null` recipes lose their env;
  `dataset-audit`/`ip-range-matcher` missing from REMOVED_PLUGINS (#141);
  non-catalog `TUT_*` not excluded; `QS_` open (#102).

## The answer key: facts, not expectations

The manifest records **facts about the node**, never predicted findings —
predictions would hand-copy the consumer's rules and drift (a built Solution is
MIGRATE or REVIEW depending on whether the build succeeds).

**We record**, in `evidence/<nickname>/seed-manifest.json` (off-node, gitignored):
identity, source (catalog URL, zip sha256, pinned version), read-back state
(installed version, interpreter, build outcome), a `synthetic` flag, and an
**intent tag naming the rule by reference** (`probe: consumer#141`,
`tp: python-envs`, `tn: visual-recipe`). **The consumer owns** expectations,
generated by its rules over our facts. **Nothing node-visible hints at intent**
—
the Planner is an LLM that reads names and descriptions.

## Delivery sequence

Measure before building; smallest useful slice first; the peer's diff of an
era-12 node is the first milestone.

### 1. Phase A1 — admin profile fix (ships alone)

The pin per licence is measured on a live node and kept locally, not published.

- **Gate `set-license` on read-back:** require licensing status 200 **and** the
  expected offer; exit 0 alone proves nothing.
- **`admin_profile_ensure`**, after `apikey_ensure`: look up the pin for the
  applied offer; if admin's stored profile is not in
  `base.userProfiles`, `dsscli user-edit admin --user-profile <pinned>`. Fail
  loudly if the pinned profile is not offered.
- **Gate by read-back:** stored profile equals the pin **and** is in
  `base.userProfiles` — `userProfile` alone reads `DATA_SCIENTIST` while demoted.
- **Repro first:** on an unfixed node, show which actions fail (a job, a
  scenario, an import owned by admin); show they pass after.
- **Fix the licence cleanup:** `docker exec -u root rm`, and assert it's gone.
- `"admin_profile"` in the provision JSON; unit fixtures for the demoted case and
  the pinned-profile-absent case.

### 2. Throwaway spike — measure (no infrastructure yet)

On one 12.x node: interpreters present; code-env creation time with and without
packages; one Solution's download → import → build, timed, keeping its import
messages; a plugin install + version read-back; dev-plugin restart cost.
**Plus: import `VFR_FLIGHT_WEATHER_PREDICTION`** (Tim's classic-recipe project,
exported from 14.7.3) — this answers whether DSS accepts a newer export into an
older node at all, which decides Phase E's scope. Output: a findings doc.

### 3. Peer review of the era-12 content mix

Send the mix and manifest schema to the consumer project;
it generates expectations on its side, and confirms whether a recently built
Solution is meant to classify MIGRATE.

### 4. Minimum seeder infrastructure

Extend `seed/dss_seed.py` in place: multipart upload, futures and job/scenario
polling, catalog fetch, plugin install by pinned zip and dev-dir, code env with
`pythonInterpreter`, and a dependency resolver shared by Solutions and ZIPs.

### 5. Era-12 content

`seed/profiles/era-12.json`, declarative. Candidate mix, finalised by the spike
and peer:

| Kind | Content | Intent tag |
| --- | --- | --- |
| Plugins | `hubspot`, `timeseries-forecast`, `openai-gpt-text-completion` (era versions) | tp: plugins |
| | `dataset-audit` or `ip-range-matcher` | probe: consumer#141 |
| | one plugin at an **old** version; a **different** plugin at current | tp / tn |
| | `xzibit` as dev plugin | tp: isDev |
| Code envs | `PYTHON36`, `PYTHON38` · `PYTHON311` · R env if the image has R | tp · tn · probe |
| Solutions | one run (MIGRATE or REVIEW, by outcome), one unrun | scope |
| Tutorials | a catalog `TUT_*`; `TUT_FOO`, `DKU_TUTORIAL_X`, a `QS_` | scope / probes |
| In scope | DEPRECATED_TESTS (`In production`) | tp: deprecated recipes |
| Scope | status set/unset; `X`, `COPYOF_X`, `X_V2`; a 3-9 digit suffix | scope |
| Existing | slices 1-3: cross-project ref, env bindings, `cpython`, `params: null` | probes #156, #93 |

One version per plugin per node; code envs without packages; plugins without
their code envs unless a seeded run needs one. Older eras are genuinely sparser
— do not normalise. History older than 180 days is the consumer's `--as-of`.

### 6. Phase E — Tim's seed projects

Five demo projects in `dss_seed_projects/` — the **in-scope** content:

| Project | Exported from | Distinctive content | Connections |
| --- | --- | --- | --- |
| `VFR_FLIGHT_WEATHER_PREDICTION` | 14.7.3 | classic recipes only; `USE_BUILTIN_MODE` with stale env name | `postgres_localhost`, `s3-managed` |
| `CHURNPREDICTIONUSINGSLACKMESSAGES` | 14.7.3 | LLM prompt + classification, evaluation | `filesystem_managed` only |
| `FINAIADVISORSTARTER` | 14.7.3 | document embedding, ML training | Snowflake, `postgres_localhost` |
| `Vulnerability_Patch_Prioritization` | 14.7.3 | document embedding | `postgres_localhost` |
| `FINANCECUSTOMERSERVICE` | **15.0.0**, 880 MB | RAG embedding, `CustomCode_text-extraction`, knowledge bank in missing project `DEMO_INTEL` | PostgreSQL, S3, `filesystem_root` |

- **Era reach is measured, not assumed.** Import each into 12.x/13.x/14.x/15.x
  one node at a time and record accept / warn / refuse. A 14.7.3 export may be
  refused by older DSS outright; if so these seed 14.x/15.x only, and the older
  in-scope content comes from DEPRECATED_TESTS. VFR is the best candidate for
  older eras; the LLM/embedding projects likely need 13+.
- **Connections:** create same-name, same-type **stub connections** so datasets
  import with their real shape. They cannot connect; builds on them fail and are
  recorded as failed. The OpenAI LLM connections are already allowed-missing.
- **In-scope signal:** none has a project status, so each would classify REVIEW.
  Set `projectStatus: In production` after import — flagged `synthetic` in the
  manifest.
- **Plugins by usage, not the export list** (which lists every plugin on the
  source instance): only `FINANCECUSTOMERSERVICE` needs one, `text-extraction`.
- **Keep the dangling `DEMO_INTEL` reference** — a dependency on a missing
  project is a real case for cross-project detection (#156); record it.
- **Budget:** import a structure-only copy of `FINANCECUSTOMERSERVICE` (bundled
  dataset data stripped, built in scratch, originals untouched) — the Planner
  never reads dataset contents.

## Controls against "reports success, produces something unusable"

| Where | Control |
| --- | --- |
| Licence | status 200 + expected offer after `set-license`; exit 0 is not evidence |
| Profile fix | failure shown on an unfixed node first; read-back against `base.userProfiles` |
| Seeder stdout | test with a stub seeder that writes stdout; `content.status` in JSON |
| Plugin installs | read back versions and zip sha256 against pins; resolver refuses to upgrade a pin |
| Imports | import messages recorded; missing-dep warnings fail the step; references must resolve |
| Budget overrun | abort the job and read back `ABORTED` |
| "Unrun" Solution | disable scenario triggers on import |
| Idempotency | compare actual settings, not names; `code_envs()` must propagate errors |
| Manifest | rebuilt from read-back every run; stamped with node identity |
| Diff validity | Planner report carries its connector version and collection status |
