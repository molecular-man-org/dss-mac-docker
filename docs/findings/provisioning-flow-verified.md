## The consumer contract actually works

Not simulated — `dataiku-headless` was pointed at the built instance **by
nickname alone**, with no credential passed between agents:

```text
switch_instance("dss-12.6.7")  →  http://localhost:11670
get_licensing_status()         →  has_license: true, valid: true,
                                  expires_at: 2026-09-29, days: 25
                                  DESIGNER unlimited, PLATFORM_ADMIN 1000
```

That is the whole point of the repo, demonstrated.

`dev-timhonker-2024.json` was accepted first try on **both** the pulled and the
built container, so the fallback walk has not yet been exercised against a real
rejection. K10 stays open for 13.x/14.x/15.x.

Expiry is checked before applying: expired files are skipped with a warning, and
`provision` refuses outright if every candidate has lapsed (K13). With 26 days
left it currently emits a warning.

## Idempotency

Re-running `provision` on an existing instance returns the **same** API key:

| Check | Result |
| --- | --- |
| Key on second run | identical to first |
| Keys labelled `dss-mac-docker` in DSS | exactly **1** |
| Instances in `~/.dataiku/config.json` | 8, no duplicates |

`apikey_ensure` reads `api-keys-list --output json`, which returns the secret
alongside the label, and reuses a matching admin key rather than minting. Without
that, every provisioning call would leave another admin key behind — DSS already
had a stray `Key generated by dsscli` from manual testing, which is exactly the
accumulation being avoided.

## K12: the config merge is safe, and it was verified rather than asserted

`~/.dataiku/config.json` holds live production credentials, so the merge was
checked against a fingerprinted snapshot taken beforehand:

| Property | Before | After |
| --- | --- | --- |
| `default_instance` | `honker1314` | `honker1314` — **untouched** |
| Instance count | 6 | 7 (then 8) |
| Instances lost | — | **none** |
| Pre-existing entries modified | — | **none** |
| API key fingerprints preserved | — | **all** |

Protections in `register_instance`:

- timestamped backup before every write
- **refuses to write** if the existing file will not parse — a corrupt config is
  not a reason to overwrite one holding real credentials
- **refuses to write** if the resulting instance set would drop any existing name
- atomic write via `mkstemp` + `os.replace`, mode `0600`
- never touches `default_instance`

## Secret handling

The API key is passed to the registration step through the environment, never as
an argv (which is visible in `ps`). Text output prints only its length; `--output
json` emits it because that is the contract, so callers must treat that stream as
a credential.
