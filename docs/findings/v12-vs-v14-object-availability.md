# What is actually absent on DSS 12 vs 14 — measured, not cited

**Date:** 2026-09-03
**Instances:** `dss-12.6.7` (11670), `dss-14.7.3` (13730), both licensed and empty
**Why:** the consumer's capability matrix asserts several object types are
unavailable on v12, and every assertion rested on a release-note citation nobody
had executed.

## What a status code does and does not prove

This distinction decides whether each row below is evidence or noise:

- **404 on v12 + 200 on v14** — the v14 result proves the URL is correct, so the
  v12 404 is evidence the object type **does not exist there**.
- **404 on both** — most likely a wrong URL guess. **Not evidence of absence.**
- **400** — the endpoint **exists** and rejected the request (missing parameter).
  A 400 is evidence of *presence*, not absence.

## Results

| Object type | 12.6.7 | 14.7.3 | Reading |
| --- | --- | --- | --- |
| agents | **404** | 200 `[]` | **Absent on v12.** Confirmed |
| semantic models | **404** | 200 `[]` | **Absent on v12.** Confirmed |
| knowledge banks | **200 `[]`** | 200 `[]` | **PRESENT on v12** |
| LLMs | **400** | 200 `[]` | **Endpoint exists on v12** — 400 is a missing param, not absence |
| scenarios | 200 | 200 | Present on both |
| saved models | 200 | 200 | Present on both |
| managed folders | 200 | 200 | Present on both |
| code studios | 200 | 200 | Present on both |
| agent tools | 404 | 404 | **Wrong URL** — confirmed, see below |
| project standards | 404 | 404 | **Wrong URL** — confirmed, see below |

The v12 `agents` 404 is an explicit `{"errorType":"NotFound"}` for
`/dip/publicapi/projects/{pk}/agents`, so the route genuinely is not registered.

The two inconclusive rows are now **confirmed wrong-path**, by independent
agreement: agent tools have a 13.4.0 minimum and project standards 14.1.0, so
both should be *present* on 14.7.3. Seeing 404 there means the path was wrong,
exactly as the status-code rules predicted.

**These probes were also at the wrong layer.** The consumer's matrix is not built
on REST routes — it gates on whether MCP tools (`list_agent_tools`, `list_agents`,
`list_semantic_models`, `list_knowledge_banks`) are exposed on a version. A
faithful re-probe should go through the SDK or MCP surface, not raw REST.

## Two results worth attention

> **Corrected 2026-09-03 after the consumer checked its actual matrix.** Neither
> result is a matrix error, and the reason matters more than the rows.

**The consumer's gates are patch-level, not major-level.** The matrix never says
"v12". It says:

| Capability | Minimum version |
| --- | --- |
| LLM Mesh inventory | 12.3.0 (pre-GA until 12.5.0) |
| Knowledge Banks and RAG | 12.5.0 |
| Agent Tool inventory | 13.4.0 |
| Project Standards | 14.1.0 |

**12.6.7 sits above every v12-era gate.** So knowledge banks being present and
the LLM route existing are exactly what the matrix predicts. These findings
*confirm* it.

**The consequence is about probe design, not the matrix.** A version at the top
of a major tests almost nothing about that major's boundaries. Measuring a gate
needs instances *below and between* the thresholds:

- **12.0.x / 12.2.x** — below the 12.3.0 LLM Mesh gate
- **12.4.x** — above LLM Mesh, below the 12.5.0 Knowledge Banks gate

**The 400 hazard stands regardless.** The LLMs endpoint on 12.6.7 returned
`MissingServletRequestParameterException` — registered, and wanting a parameter.
Any collector treating 400 as "not available" would manufacture a false absence.

## Project settings differ strictly additively

Comparing the same project's settings across eras: **five keys on 14.7.3 absent
on 12.6.7, and none the other way**.

```text
+ agentInteractionLoggingSelection      + connectionValidationChecks
+ autogeneratedDocumentationEnabled     + visualRecipesEnginesSettings
+ cobuildSettings
```

Two are agent-related, consistent with agents being a v14 concept. 24 keys shared.

## Code env binding keys are asymmetric

At **project** level the key is `mode`, identical on both eras:

```json
"codeEnvs": {"python": {"mode": "INHERIT", "preventOverride": false}, "r": {...}}
```

The consumer reports the **recipe**-level key is `envMode`, not `mode` — a
defect they already shipped a fix for. The project-level shape above confirms the
asymmetry is real rather than a misreading: the same concept is spelled
differently at the two levels. Recipe-level confirmation needs a code recipe,
which is seeding slice 2.

## Open hypothesis: route registration as a cheap screen for gate errors

Arising from the Knowledge Banks result, and worth testing deliberately rather
than leaving as an anecdote.

**Hypothesis:** whether a REST route is registered on a version predicts whether
a capability gate defined at the MCP layer is wrong.

**Why it would matter — the economics.** The consumer has roughly ten capability
gates, every one currently a citation nobody has executed. Verifying one properly
means a correctly-bracketed instance pair and an MCP-layer check: slow. A route
probe needs no seeding, no bracket, and takes seconds. If the correlation holds,
it turns "verify ten gates" into "verify the two the screen flags".

It would be a **screen, not a proof** — the layers are genuinely different,
and a
route can legitimately exist before a capability is available (the consumer's own
LLM Mesh entry is annotated "pre-GA until 12.5.0").

**The first data point is Knowledge Banks at 12.4.2, and it is informative either
way:**

| Outcome at the MCP layer | What it teaches |
| --- | --- |
| Gate also wrong | Route registration predicted a real error — build probes around it |
| Gate right, route early | The screen over-reports; we learn its false-positive rate from a case with known ground truth |

A hypothesis whose disconfirmation is also useful is worth running. One that only
pays off if true is a hope.

**Prerequisite if it is pursued:** the two inconclusive rows above must be
resolved first. A screen built on guessed URLs would report absence wherever the
path was simply wrong — the same false-negative shape, industrialised.
